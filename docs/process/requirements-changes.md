# Requirements Changes

Each entry: date, change, reason, source. Changes before 2026-10-01 are reconstructed from `docs/handoff.md`.

| Date | Change | Reason | Source |
| --- | --- | --- | --- |
| before 2026-10-01 | Automatic daily digest → manual "Generate Digest" covering the period since the last successful request | Simpler first release; users who check less often still get everything since their last digest | handoff §4 |
| before 2026-10-01 | Scope narrowed from "any website" to selected public sites/blogs and podcasts/videos with accessible transcripts | Arbitrary scraping is unreliable; summarizing audio/video without transcripts would overclaim | handoff §3 |
| before 2026-10-01 | Bookmarks, likes, feedback moved after the core workflow (still planned, not dropped) | Core collect → digest flow comes first | handoff §4 |
| before 2026-10-01 | Browser extension, logged-in content, page-change detection, scheduling → stretch / later | Keep the initial release achievable | handoff §4 |
| 2026-10-02 | No per-run limit on how many new items a digest covers (a proposed cap of 50 was rejected) | User wants every new item included after a long gap; progress display and batched topic grouping handle volume instead | User feedback on `add-core-digest-flow` proposals |
| 2026-10-02 | New future feature: let the user choose to output only the N most important items | User request; per-item summaries in the chosen design make ranking possible later | User feedback on `add-core-digest-flow` proposals |
| 2026-10-02 | Digest language is chosen by the user in Settings during initial setup (English, Simplified Chinese, same as original, or another language), instead of an environment variable defaulting to English | User request; the audience is not English-only. Cached item summaries now record their language so a language change re-summarizes instead of mixing languages | User feedback on the `add-core-digest-flow` plan |
| 2026-10-02 | Feed discovery also probes common feed locations (page URL + `.rss`, `/feed`, `/rss.xml`, `/atom.xml`, ...) when a page declares no feed | Sites like Reddit expose RSS without declaring it; users should be able to paste the normal page URL | User decision during `add-core-digest-flow` planning |
| 2026-10-02 | Text-based social media: Bluesky, Mastodon, and Reddit are supported through their RSS feeds in the first release; X is not supported | Verified live: Bluesky and Mastodon profiles declare RSS, and Reddit serves `/.rss`. X needs login (scraping is against its terms) or the paid X API ($0.005 per post read, no free tier, docs.x.com). Later options: a user-supplied X API key, or the browser extension | User question; decision to defer X pending the alpha |
| 2026-10-03 | The stored API key is used only with its stored base URL, and the instance accepts requests only for allowed hosts (`CATCHUP_ALLOWED_HOSTS`) | Review found that a DNS-rebinding page could repoint the provider URL and receive the stored key. The original design let missing fields fall back to stored values | Claude Code review of groups 2–3 |
| 2026-10-03 | Added requirements: readable titles for untitled entries; summaries focus on substance without metadata; output budgets that work with reasoning models; whole-site notice not shown on profile pages | First real test with DeepSeek and public sources (Bluesky, Mastodon, Reddit, a blog) found issues that mocked tests could not | Manual verification of `add-core-digest-flow` |
| 2026-10-03 | Deferred: extracting the linked article for Reddit link posts; Reddit rate-limit handling; a per-provider thinking toggle | Real-source behavior; larger than a fix | Manual verification of `add-core-digest-flow` |
| 2026-10-04 | Change `improve-source-reliability` narrowed to generic fetch reliability (User-Agent, 429/Retry-After, no duplicate fetch on confirm). The Reddit link-post extractor (#2) was dropped, and the README will state that Reddit support ends 2026-11-13 | Research found Reddit will stop all RSS on 2026-11-13 (TechCrunch 2026-09-30; Reddit Help Center), before the 2026-12-10 final demo. The generic work benefits every source | User decision after research |
| 2026-10-04 | "Deployed demo for course evaluation" (proposal) becomes local deployment: Docker image + setup docs, demo run on the developer's machine; no hosted instance | Course staff confirmed on the course forum that a locally deployed project is fine. Hosting would add access control and cost and would hit cloud-IP blocking | Course forum (staff answer); user decision |
| 2026-10-04 | Podcasts (#5) and YouTube (#6) are planned as one change, `add-podcast-and-video-sources` (renamed from `add-youtube-sources`). Long transcripts must be summarized in full: today every item is cut to `CATCHUP_MAX_ITEM_CHARS` (20,000 characters), which keeps about 12% of a 3.6-hour episode | Both share the same rule (summarize only with a transcript, otherwise mark the item unsupported), the same new item state and display, and the same long-text problem. One change avoids building them twice | User decision after the YouTube research |
| 2026-10-05 | Items that cannot be summarized appear once in a "Creator updates" section after the topic summaries: grouped by creator or show; title, publication time, link, and a reason (caption fetching off, video has no captions, blocked by YouTube, captions could not be fetched, no podcast transcript within 7 days); no model call; Shorts excluded. Podcast episodes without a transcript are held back for up to 7 days and re-checked each run; YouTube items without captions are listed at once. Every item appears in exactly one digest. Replaces the planned "Not summarized — no transcript" list | A neutral, useful listing of what creators published is better than a failure list. The earlier design either repeated waiting items in every digest or stopped re-checking them once listed | User decision on the `add-podcast-and-video-sources` proposals |
| 2026-10-05 | The single-call text budget for summaries is derived from the model's `context_window` reported by `/models` (fallback 60,000 characters), instead of a fixed character cap; longer texts are chunked and combined. YouTube captions use the video's original language (manual over auto-generated, never machine-translated), and caption fetching is sequential, spaced, and capped per run | Long transcripts must be summarized in full without assuming one model's context size; the captions library bypasses `safe_fetch`'s spacing and rate-limit handling | User decision on the `add-podcast-and-video-sources` proposals |
| 2026-10-05 | YouTube videos without captions yet (no caption tracks, or not playable yet such as upcoming premieres) wait up to `CATCHUP_CAPTION_WAIT_HOURS` (default 24) and are retried on each run before being listed once under Creator updates. This amends the earlier rule that caption failures are listed immediately; blocked requests and other failures are still listed at once | The plan review raised that fresh uploads may lack auto-captions; the caption library reports "no caption tracks" the same way for uploader-disabled and not-yet-generated captions | User decision after the independent plan review |
| 2026-10-05 | A link carried by more than one entry of the same feed is no longer used to identify, deduplicate, or match entries; such entries without a feed id are identified by title and date | Implementation review: The Daily (64 episodes) and a Captivate show (121) give every episode the show's home-page link, so the v0.1 link dedup recorded only the first episode, and the new transcript matching gave episodes a sibling's transcript | Claude Code review of `add-podcast-and-video-sources` with an independent subagent; live feed check |
| 2026-10-06 | New `user-interface` requirements: one aligned grid; themes following the system with AA contrast; the digest reading layout; one primary action per state; state-aware side information; inline delete confirmation; saved key shown by its last four characters; keyboard and screen-reader support. CatchUp becomes installable with an offline page. Saved digests record their language and item source kinds | The UI/UX redesign (#24) chosen by the user (C7) after prototype rounds and a Design plugin review; D-014 (installable PWA) | User choice and approval on `redesign-ui-ux` |
| 2026-10-06 | `user-interface`: "one primary action per state" becomes "at most one"; a state where nothing needs doing next (a run with no new content) offers none. The error color shifts toward orange so error, warning, and accent hues differ by at least 20° | Factory Droid stopped before implementing and reported that the plan required exactly one primary action while the design gave No new content none, and that the planned 20° hue test failed on the planned colors; Claude verified both | User decision after Droid's report on `redesign-ui-ux` |
| 2026-10-07 | `digest-history` "List saved digests": each listed digest also shows its edition number and topic titles, a Creator-updates-only digest is labeled as such, and the list comes from a single request | The implementation review found that History fetched every digest's full detail to show previews (N+1 requests, and one failure hid the whole list) | User decision (A1) after the `redesign-ui-ux` review |
| 2026-10-07 | `user-interface`: a "no sources yet" state on Generate (primary action "Add sources"); each screen has its own document title; a run failure is announced once; "Digest ready: N items" counts Creator updates. Feed URLs are shown in full (the design's 2-line clamp is dropped to match the spec) | Final review of the whole `redesign-ui-ux` change with `/code-review` and an independent spec review | User decisions A and B after the final review |
| 2026-10-16 | `user-interface`: the main screen shows the newest saved digest in the reading layout, with a run bar above it, and its navigation item is named "Latest"; a saved digest replaces the shown one without moving focus; the finished-digest state has no primary action ("View digest" is removed); no side rail beside a shown digest; main-screen titles name the shown edition. `digest-history`: the newest digest can be fetched with one request | Reading is the main activity; after each run the user had to open the digest from "View digest" or History | User request in issue #27 (2026-10-14); Proposal 1 chosen on 2026-10-16 (D-017) |
| 2026-10-16 | `user-interface` "Digest reading layout": the rule that a long item gets a wider column than a short one is replaced. On wide windows each item is a row with its source line and title beside its summary, and every summary has the same width and ends at the content's right edge. At 1440 px a summary line holds at most 40 Chinese or 80 Latin characters. At 1100 px and below, an item stacks its source line, title, and summary (decided after review), and below 900 px everything is one column. Grouping granularity is split out to #32 | Almost every real summary counted as long, so most rows left the right third of the content empty; since D-017 this is the main screen | Issue #25; Proposal 1 chosen on 2026-10-16 (D-018) |
